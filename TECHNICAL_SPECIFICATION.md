# Техническая спецификация Vacancy Collector v1.0

## Вход

Обработчик читает локальные JSON и CSV из `input/`. Обязательные поля каждой записи — `Source`, `External_ID` и `Vacancy_Title`. Общая схема применяется ко всем источникам. Преобразование схемы конкретного поставщика выполняется до передачи файла обработчику.

- JSON содержит массив вакансий или объект с массивом `items`.
- Входной CSV использует UTF-8 с BOM или без него и разделитель `;`.
- Для `Published_At` принимаются дата `YYYY-MM-DD` и дата-время ISO 8601 с явным часовым смещением или `Z`. Некорректная дата, включая дату-время без часового пояса, даёт `REJECTED` и направляется на уточнение. Отсутствующая дата публикации остаётся пустой.
- Служебные отметки, включая создаваемые обработчиком `Collected_At`, `Status_Changed_At` и время событий журнала, отражают фактическое время операции и сохраняются в UTC в формате ISO 8601 с `Z`.

Нормализация включает удаление внешних пробелов из обязательных текстовых полей и приведение допустимых значений к согласованным форматам. `External_ID` обрабатывается как текст с сохранением регистра и ведущих нулей. Пустое или отсутствующее обязательное поле направляет запись на уточнение. Для отсутствующего `External_ID` запрещено вычислять замену по названию, работодателю или URL. Допустимые пустые необязательные поля сохраняются пустыми.

## Реестр

Файл `data/vacancies_registry.csv` использует UTF-8 с BOM и разделитель `;`. Заголовок и порядок полей фиксированы.

1. `Internal_ID`
2. `Source`
3. `External_ID`
4. `Vacancy_Title`
5. `Employer`
6. `Location`
7. `Work_Format`
8. `Employment_Type`
9. `Salary_From`
10. `Salary_To`
11. `Salary_Currency`
12. `Published_At`
13. `Collected_At`
14. `Vacancy_URL`
15. `Record_Status`
16. `Status_Changed_At`

Допустимые значения `Record_Status`:

- `ACTIVE` — активная запись.
- `EXCLUDED` — запись, которую пользователь исключил из дальнейшего анализа.
- `ARCHIVED` — архивная запись.

Физическое удаление записей запрещено.

## Режим IMPORT

Уникальный ключ — пара нормализованных значений `(Source, External_ID)`. Проверять повторы как в пределах входного файла, так и по реестру. Новому ключу присваивать следующий последовательный ID в формате `VC-000001`, начиная с максимального номера в реестре плюс один, либо с единицы для нового реестра. Новая запись получает `ACTIVE` и фактическое время присвоения статуса в `Status_Changed_At` в формате ISO 8601.

| Результат | Условие и действие |
| --- | --- |
| `ADDED` | Новый ключ с допустимой записью. Добавить вакансию в реестр. |
| `DUPLICATE` | Ключ уже зарегистрирован, все нормализованные содержательные поля совпадают. Сохранить запись без изменений. |
| `CONFLICT` | Ключ совпадает, хотя бы одно нормализованное содержательное поле отличается. Сохранить существующую запись без изменений и направить расхождение на уточнение. Если ключ новый и в одном файле есть конфликтующие варианты, направить на уточнение всю группу без добавления. |
| `REJECTED` | Запись нарушает требования к данным, например отсутствует обязательное поле или передана некорректная дата. Направить запись на уточнение. |

Для одинакового ключа сравнивать `Vacancy_Title`, `Employer`, `Location`, `Work_Format`, `Employment_Type`, `Salary_From`, `Salary_To`, `Salary_Currency`, `Published_At` и `Vacancy_URL`. Исключить из сравнения `Internal_ID`, `Collected_At`, `Record_Status` и `Status_Changed_At`.

- В текстовых полях удалять внешние пробелы и сохранять смысл текста, в том числе регистр, пунктуацию и значимые внутренние пробелы. `Source` и `External_ID` сравнивать как отдельные компоненты ключа.
- `Salary_From` и `Salary_To` сравнивать по точному десятичному значению. Например, `1000` и `1000.00` равны.
- Даты без времени сравнивать как календарные даты, даты-время со смещением — по одному и тому же моменту в UTC. Дата без времени имеет собственную точность и не приравнивается к полуночи. Пустые даты и числа остаются пустыми.

При повторном импорте той же вакансии `DUPLICATE` и `CONFLICT` сохраняют существующую запись целиком. Если в запуске нет добавлений, файл реестра не перезаписывается. Каждый повторный запуск получает собственный `Run_ID` и артефакты, даже если реестр не меняется.

## Режим MANAGE

Режим применяется по явному запросу пользователя. Источник команд — `input/record_actions.csv` с заголовком `Internal_ID;Action;Reason`. Для файла команд действуют те же правила кодировки и разделителя, что и для входного CSV. `Reason` обязательно и должно содержать непробельный текст для `EXCLUDE` и `ARCHIVE`. Для `RESTORE` допускается пустое значение.

| Action | Новый Record_Status |
| --- | --- |
| `EXCLUDE` | `EXCLUDED` |
| `ARCHIVE` | `ARCHIVED` |
| `RESTORE` | `ACTIVE` |

Проверить файл команд целиком до применения изменений. Нечитаемый файл, неверный заголовок или повреждение структуры останавливают обработку файла без изменений реестра. До применения команд сгруппировать строки пакета по `Internal_ID`. Если для одного ID поступило несколько команд, отклонить всю группу, включая совпадающие команды. Остальные корректные команды могут выполняться. Команда с неизвестным `Internal_ID`, недопустимым `Action` или отсутствующей обязательной причиной отклоняется с записью причины в журнал. Изменение статуса допустимо только для существующей записи по явной допустимой команде. При фактической смене статуса записать время операции в `Status_Changed_At` в UTC с `Z`. Команда на уже установленный статус оставляет запись и её отметку времени прежними. Повтор того же пакета без промежуточных изменений не приводит к новым сменам статусов или перезаписи реестра. Успешное изменение фиксируется в журнале после сохранения реестра.

## Запись и защита данных

- В обоих режимах до записи разобрать входной файл целиком и проверить действующий реестр, включая заголовок, уникальность ключей и ID, допустимость статусов и корректность отметок времени статуса. При повреждении структуры входного файла или действующего реестра завершить запуск без изменений реестра и зафиксировать причину в журнале. Ошибки отдельных записей в структурно корректном файле не блокируют обработку остальных корректных записей.
- Сериализовать операции чтения и записи реестра между запусками. Писать обновление во временный файл рядом с реестром, закрыть его, проверить схему и инварианты, затем выполнить атомарную замену. При ошибке до замены действующий реестр должен сохраниться. Согласовать обновление существующего файла до записи.
- На Windows блокировка удерживается ОС на первом байте постоянного файла `data/vacancies_registry.lock` от чтения реестра до проверки результата записи. Конкурирующий запуск завершается с ошибкой блокировки. После аварийного завершения процесса ОС освобождает блокировку. Файл блокировки сохраняется между запусками и не удаляется по возрасту.
- Для CSV, предназначенных для открытия в Excel, использовать штатное экранирование CSV и нейтрализовать формулы в пользовательских значениях. Если значение начинается с `=`, `+`, `-`, `@` или управляющего символа (табуляция, CR, LF), либо первый значимый символ после начальных пробельных и управляющих символов является маркером формулы, добавлять ведущий апостроф. Ведущий исходный апостроф экранировать дополнительным апострофом. При чтении собственного реестра снимать только добавленный префикс по тому же правилу, чтобы сравнивать исходные значения ключей. CSV-кавычки обеспечивают структуру полей, а префикс защищает от выполнения формул. Для сохранения ведущих нулей при просмотре CSV импортировать `External_ID` в Excel как текст.

## Журнал и уточнение

Каждому запуску присваивается уникальный `Run_ID`. Для запуска создаются структурированный JSON-журнал в `outputs/logs/`, читаемый Markdown-отчёт в `outputs/reports/` и отдельный перечень записей на уточнение в `outputs/reports/`. Имена и содержимое всех трёх артефактов включают общий `Run_ID`. Предыдущие результаты сохраняются без перезаписи. Перечень связывает запись или расхождение с входным файлом, номером записи и причиной. Исходные файлы читаются без изменения.

Имена файлов — `run_<Run_ID>.json`, `run_<Run_ID>.md` и `needs_review_<Run_ID>.csv`. Перечень использует UTF-8 с BOM и разделитель `;`. Его поля — `Run_ID`, `Input_File`, `Record_Number`, `Result`, `Reason`, `Source`, `External_ID`, `Record_JSON`. При отсутствии записей на уточнение общий `Run_ID` остаётся в имени CSV, а CSV содержит только заголовок.

Журнал фиксирует время запуска, режим `IMPORT` или `MANAGE`, путь входного файла, итог, количество обработанных записей или команд, счётчики `ADDED`, `DUPLICATE`, `CONFLICT`, `REJECTED` и ошибки. Для каждой сохранённой смены статуса указываются `Internal_ID`, команда, прежний и новый статусы, время и причина.

В режиме `MANAGE` журнал и Markdown-отчёт дополнительно содержат счётчики `CHANGED` и `UNCHANGED`. JSON-журнал включает списки `Status_Changes` и `Unchanged_Commands`. CSV отклонённых команд дополнительно содержит `Internal_ID`, `Action` и `Command_Reason`. Поле `Reason` этого CSV содержит причину отклонения. Номер записи отсчитывается от первой строки данных, без заголовка.

Для состояния реестра до и после операции журнал фиксирует общее количество записей, количества по каждому из `ACTIVE`, `EXCLUDED`, `ARCHIVED` и SHA-256 фактических байтов файла, включая BOM, через `hashlib.sha256` стандартной библиотеки Python. Для отсутствующего файла указывать нулевые количества и отсутствие контрольной суммы. Если состояние нельзя прочитать или проверить, отметить недоступные значения и записать причину. При запуске без изменений существующего реестра доступные показатели до и после совпадают.

## Границы версии

Версия 1.0 работает с локальными файлами и использует Python 3.13.5 со стандартной библиотекой. Установка программ и зависимостей и изменение системных настроек запрещены. Внешние API, автоматические отклики, AI-оценка вакансий и запуск по расписанию исключены из объёма версии. В CDsk01-01B.1 обновляется документация. Реализация и функциональные проверки относятся к CDsk01-01B.2 и требуют отдельного согласования.
